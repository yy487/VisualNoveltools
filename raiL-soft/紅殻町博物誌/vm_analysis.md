# GSC / VM 分析记录

本文档记录《紅殻町博物誌》74 个 GSC 样本与宿主程序反编译交叉验证后的结论。“已确认”表示样本边界、引用或 VM 调用链已能闭合；“待确认”表示还不应写入正式 opcode 字典。

## 样本与依据

- GSC 样本：`E:\GAL\紅殻町博物誌\work\scr_unpacked`
- EXE 反编译：`E:\GAL\紅殻町博物誌\work\紅殻町博物誌.exe_export_for_ai`
- 全部样本均为小端序，文本编码为 CP932。

## GSC 文件结构

GSC 不只有“指令区 + 文本池”两个物理区域。文本本地化主路径确实由指令区、文本索引和文本池构成，但文件后部还有 `u16` 序列表和符号表。

文件头固定 36 字节：

| 偏移 | 大小 | 已确认含义 |
|---:|---:|---|
| `0x00` | 4 | 文件总字节数 |
| `0x04` | 4 | 文件头大小，固定 `36` |
| `0x08` | 4 | 指令区字节数 |
| `0x0C` | 4 | 文本偏移表字节数，每项 `u32` |
| `0x10` | 4 | CP932 NUL 结尾文本池字节数 |
| `0x14` | 4 | `u16` 序列偏移表字节数，每项 `u32` |
| `0x18` | 4 | `u16` 序列池的元素数，物理大小为该值的 2 倍 |
| `0x1C` | 4 | 符号项表字节数；后部有两张同样大小的 `u32` 表 |
| `0x20` | 4 | 符号名 CP932 NUL 结尾字符串池字节数 |

`0x24` 之后按顺序排列：

1. 指令区。
2. 文本偏移表。
3. 文本池。
4. `u16` 序列偏移表。
5. `u16` 序列池。
6. 符号名偏移表。
7. 符号值/指令偏移表。
8. 符号名字符串池。

因此文件大小必须满足：

```text
file_size = 36
          + code_size
          + text_index_size
          + text_pool_size
          + sequence_index_size
          + 2 * sequence_pool_count
          + 2 * symbol_table_size
          + symbol_name_pool_size
```

74/74 个文件的声明大小、物理大小和上式计算值完全相等。`sub_413AE0` 证实第 4/5 区是按索引访问的 `u16` 序列；`sub_413A00` 证实最后三区用符号名查找对应值。例如 `0001.gsc` 的符号 `omakemenu` 映射到指令偏移 `0x386`。

## 文本索引与分隔

`sub_413AC0(vm, index)` 的逻辑是：

```c
return vm->text_pool + *(u32 *)(vm->text_index + 4 * index);
```

全部 74 个文件共有 8,461 个文本索引项：

- 每个索引值都在文本池范围内。
- 每个索引都指向一个 NUL 结尾字符串的起点。
- 索引顺序与文本池中字符串的物理顺序一致。
- 每个文件的索引 0 均指向空字符串。

真正的文本记录分隔符是单字节 `00`：

- 文本池中 `42 00` 共出现 3,128 次，每次前一字节都是 `81`，完整序列为 `81 42 00`，即 CP932 的 `。` 加 NUL。
- 在正确边界的文本池中，`72 00` 出现 0 次。
- 因此 `42 00` 和 `72 00` 都不是翻页或同页分段符。

每个 NUL 字符串是一条可索引的逻辑文本记录。新页、续显、清空和等待属于 VM 指令和消息窗口状态，不由文本池的特殊字节对分隔。

## VM 取指与文本指令

`sub_41BD00` 是主解释器。`sub_413A60` 读取一个有符号 16 位 opcode，`sub_413A80` 读取有符号 16 位操作数，`sub_413AA0` 读取 32 位操作数。opcode 高半字节非零时还存在按 `0x1000..0xF000` 分派的编码族，所以不能对指令区直接搜索两字节 opcode 并当作已对齐指令。

### `0x0051` 主消息指令

`case 81` 在 opcode 后读取 7 个 32 位操作数，总长度 30 字节。第 6 个操作数是已确认的文本索引：

```text
0x0051 op1 op2 op3 op4 op5 text_index op7
```

调用链：

```text
sub_41BD00 case 81
  -> sub_41F020(..., text_index, ...)
  -> sub_42D790(...)
  -> sub_413AC0(vm, text_index)
```

已确认/可见行为：

- `op5` 在当前运行时中被读取后丢弃。
- `op6` 是文本索引。
- `op2/op3/op4` 进入语音资源与序号处理，但准确字段名仍待语音指令链完整命名。
- `op1/op7` 参与消息窗口和显示后等待/清理逻辑，尚不应给出过度具体的名称。

### `0x0052` 次消息路径

`case 82` 读取 6 个 32 位操作数，总长度 26 字节。第 5 个操作数是文本索引：

```text
0x0052 op1 op2 op3 op4 text_index op6
```

它通过 `sub_41EEB0 -> sub_42D790` 显示文本，与 `0x0051` 的差异是：

- 不设置 `0x0051` 的语音/等待参数。
- 以 `n2 = 0` 进入 `sub_42D790`，不重新执行行首 `【`的说话人检测，而是继承前一消息状态。

这些行为与“续显/次要消息”相符，但在完整对齐解码器统计 74 个样本之前，不把它正式命名为“同页分段”。当前直接搜索到的 `52 00` 会包含操作数中的假阳性。

### 相关消息控制

- `0x0050` 读取 1 个 32 位操作数，通过 `sub_41EE80 -> sub_42D9D0` 清理/复位当前消息。
- `0x0053` 读取 1 个 32 位操作数，也会进入消息清理链，并额外改变解释器调度状态。它的准确“等待/翻页”助记符待对齐指令流和运行时测试确认。

## 选项与跳转结构

### `0x000E` 选择指令

`sub_41BD00 case 14` 是已确认的选择指令。它固定长 60 字节，一条指令内同时保存最多 5 个选项文本索引和 5 个分支目标：

| 相对偏移 | 大小 | 含义 |
|---:|---:|---|
| `+0x00` | 2 | opcode `0x000E` |
| `+0x02` | 2 | 低 8 位为选项数，高 8 位为尚未命名的标志 |
| `+0x04` | 4 | 选择提示/标题的文本索引 |
| `+0x08` | `5 * 4` | 5 个分支目标，仅前 `count` 项有效 |
| `+0x1C` | `5 * 4` | 5 个选项文本索引，仅前 `count` 项有效 |
| `+0x30` | `3 * 4` | 选择界面模式/布局参数，当前样本均为 0 |

运行时调用链：

```text
sub_41BD00 case 14
  -> sub_4209F0
  -> sub_411970             创建选择界面
  -> sub_4120E0             返回 1 起始的选项序号
  -> targets[selected - 1]
  -> sub_41BCB0
  -> sub_413B20             IP = code_base + target
```

因此选项目标是“相对指令区起点的绝对偏移”，不是相对当前指令或下一条指令的位移。GSC 中的文件偏移等于该目标加 `0x24`。

经该布局和目标边界验证，74 个 GSC 中共有 24 条对齐的 `0x000E`，包含 49 个有效选项槽，与文本池中全部 49 条 `<...>` 选项字符串完全对应。当前样本的选项数为 1、2、3 或 4，高 8 位标志、提示文本和末尾三参数均为 0。

### `<01>` 选项样式前缀

选项池中的文本实际为 `<01>有り難く...` 这类结构。`sub_4109C0` 在展示前会从尖括号中读取数值，选择 `sel_a01` 界面资源，再把尖括号之后的部分作为可见选项文本。因此 `<01>` 是选项样式 ID，不是显示文字。

正式 JSON 可将可见部分放入 `scr_msg/message`，同时用内部字段 `_choice_style: 1` 保留并重建 `<01>`；注入前仍需对“前缀 + `scr_msg`”进行原始字节校验。

### 八组二选一分支

用户给出的文本实际是 8 个独立选项，分布在 7 个 GSC 的 8 条 `0x000E` 指令中（`1303.gsc` 有两条）。每个直接目标先进入一段 22 字节的状态写入跳板：`A800 -> 1900 -> F100`。正向选项将对应变量写为 1，反向选项写为 0，随后通过 `0x0005` 绝对跳转或顺序落入后续剧情。

| 状态变量 | GSC / 选择指令 | 正向选项：文本索引 -> 直接目标 -> 后续 | 反向选项：文本索引 -> 直接目标 -> 后续 |
|---:|---|---|---|

| `0x7D2` | `1406.gsc @ 0xB72` | 74 `この町は、今のままが良いと感じた` -> `0xBB4` -> `0xBF2` | 75 `時代の流れには、逆らえないと思った` -> `0xBD6` -> `0x1084` |
| `0x7D3` | `1303.gsc @ 0x5FA` | 33 `内心を素直に白状した` -> `0x63C` -> `0x67A` | 34 `やはり黙っておくことにした` -> `0x65E` -> `0x752` |
| `0x7D4` | `1303.gsc @ 0x19D2` | 172 `先に降り、エミリアに手を差し延べる` -> `0x1A14` -> `0x1A52` | 173 `まず舟を舷う` -> `0x1A36` -> `0x1F26` |
| `0x7D5` | `1502.gsc @ 0x11FE` | 117 `松実の手を、握り返した` -> `0x1240` -> `0x1272` | 118 `松実の手を、そっと離した` -> `0x125C` -> `0x1272` |

### `1601.gsc` 候选人聚合

`1601.gsc` 在指令偏移 `0x1988` 开始将八个状态变量两两相加，只有和大于等于 2，也就是同一角色的两个正向选项都被选中时，才把她加入最终候选：

```text
白子       eligible = state[0x7D1] + state[0x7D2] >= 2
エミリア eligible = state[0x7D3] + state[0x7D4] >= 2
松実       eligible = state[0x7D5] + state[0x7D6] >= 2
十湖       eligible = state[0x7D7] + state[0x7D8] >= 2
```

随后的 16 条 `0x000E` 分别覆盖四位角色的 15 种非空子集，以及无人合格时的 `誰も思い浮かばない`。选中后，`0x1800` 赋值跳板会将最终对象编号写入 `state[0x7D0]`：

| `state[0x7D0]` | 最终对象 |
|---:|---|
| 1 | 白子 |
| 2 | エミリア |
| 3 | 松実 |
| 4 | 十湖 |
| 5 | 誰も思い浮かばない |

### 基础跳转 opcode

- `0x0003 target:u32`：当 VM 临时值 0 为 0 时，跳到指令区绝对偏移 `target`。
- `0x0004 target:u32`：当 VM 临时值 0 非 0 时，跳到指令区绝对偏移 `target`。
- `0x0005 target:u32`：无条件跳到指令区绝对偏移 `target`。

三者都固定长 6 字节，最终反汇编必须将其目标标签化，重汇编时再按标签的新指令区偏移回填。

## 说话人标记

CP932 `【` 的字节为 `81 79`。EXE 内存 `0x47EE94` 正是 `81 79 00 00`，`sub_42D790` 会比较展开后文本的前两字节是否为该标记，然后设置名字/消息状态。

文本池统计：

- 4,454 条字符串以 `【` 开头，且全部包含 `】`。
- 4,452 条符合 `【name】^n...`，可安全拆出 `name`。
- 另两条是章节标记，不是说话人：`1605.gsc` 中的 `【以下：青年の回想】` 和 `【青年の回想：ここまで】`。

导出时只对严格以 `【name】^n` 开头的结构输出 `name`。仅因为文本以 `【` 开头就猜测说话人会错收上述两个标记。

## 文本控制与排版

`sub_41D7E0` 先执行运行时展开：

- `@...`：数值表达式展开。
- `$0..$9`：字符串槽位展开。

它不会删除脱字号控制码，这些控制码由 `sub_4543A0/sub_454B60` 和其他同类渲染器处理。样本中观察到：

```text
^n  11,662
^d      62
^s       1
```

### `^n` 强制换行

`^n` 不生成可见字形，而是在当前字形位置的元数据 `+1` 字节写入换行标志。`sub_455400` 排版时会读取该标志并立即结束当前行。

### `^dN` 逐字显示延迟

`^d` 后必须跟一个数字。解析器将延迟值写入每个字形的 6 字节元数据中：

```text
^d0 -> 0
^dN -> base_delay + 2 * (N - 1), N > 0
```

`sub_4561C0` 在逐字显示时读取该值：非零时为字形启用出现效果，并在显示下一字前设置计时。因此 `^d0` 是关闭逐字延迟，`^d1` 是恢复基础延迟，与分页无关。

### `^sN` 字号倍率

`^s` 后必须跟一个数字。`sub_4543A0` 保存该倍率，`sub_454FC0` 按基础字号计算后续字形尺寸：

```text
^s0 -> 0.5 * base_size
^s1 -> 1.0 * base_size
^s2 -> 1.5 * base_size
^s3 -> 2.0 * base_size
^sN -> (N - 1) * base_size, N > 3
```

当前唯一的 `^s` 样本是 `1501.gsc` 的 `^s0`。某个备用渲染路径只消费而不应用该参数，但主字形路径的字号计算已确认。

### 自动换行与日文禁则

游戏存在自动换行。`sub_455400` 逐字累加字形宽度和字距，与当前文本框宽度比较，超出时生成新行；它同时优先处理 `^n` 标志。`sub_454FC0` 还会对句读点、括号、促音/拗音等写入行首行尾禁则类别，`sub_455400` 溢出时会依此回退分行位置。

样本中最长的无 `^n` 文本长 390 个 Unicode 字符（`1401.gsc` 文本索引 38），也从脚本侧证明排版必须依赖自动换行。

### 振假名

渲染器将 `[reading]` 解析为前一个基文字的振假名；`|` 会先记录一个跨字符基文本的起点，例如 `|倫敦[ロンドン]`。全部文本池中有 1,503 条包含 `[...]`，984 条包含 `|`。提取和注入必须原样保留这些标记。

## 对文本工具的约束

- 正式提取以对齐 VM 指令引用的文本索引为依据，不仅扫描文本池。
- JSON 使用 UTF-8，原文写入 `scr_msg`，可编辑副本写入 `message`。
- `_index` 保存 GSC 文本索引，`_offset` 保存文本池内或文件内偏移，`_inst_offset` 保存引用指令偏移。
- `^n/^dN/^sN`、`|`、`[...]`、`@...` 和 `$0..$9` 都属于必须保留的脚本语义。
- 只在文本严格以 `【name】^n` 开头时拆出 `name`；注入时必须重建原标记。
- 变长注入至少需要重建文本池和文本偏移表，并更新文件总大小及外层 XFL 文件表。其他区域必须原样保留。

## 待确认项

文本工具现已实现为独立的文本池重建流程：它不改变指令区长度，因此不依赖全量 opcode 字典，也不需要重算选择和跳转目标。74 个 GSC 的零修改逐字节回环、真实变长选项/对话测试及 XFL 整包回环均已通过。下面的待确认项只影响未来的完整语义反汇编/重汇编功能，不阻塞当前 JSON 提取和变长注入。

1. 从指令区起点完整对齐解码 74 个 GSC，建立全量 opcode 长度和操作数表。
2. 统计已对齐的 `0x0051/0x0052`，确认 `0x0052` 在本作脚本中的实际使用场景。
3. 确认 `0x0050/0x0053` 在一页消息生命周期中的准确助记符和等待时机。
4. 继续确认调用、返回和其他条件分支，然后才能安全实现全量语义反汇编与变长回环。
